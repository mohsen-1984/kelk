## 3. Decisions

1. **What a golden holds:** the HTML export, the `.docx`'s XML (all parts; since the review also `docProps/`, with
   `core.xml`'s created / modified dates as `[date]`), the `.doc`'s parts, the PDF read back as Markdown, and the
   `.docx` read back as Markdown — not PDF bytes or glyph positions (fonts and timestamps).
2. **Raster pictures: type, size, and bytes only when they are the input's.** A formula's PNG fallback is drawn on a
   canvas, whose anti-aliasing differs between platforms, so the bytes of a picture the builder drew are not kept —
   its type and the width × height in its header are. A picture taken unchanged from the case's input is kept as its
   hash too, so a damaged or swapped picture fails (the first version kept only the type: a builder writing 40-byte
   pictures would have passed — review finding 1). A header that does not decode is written "NOT DECODABLE". SVG,
   fonts and other vector data are kept as size + SHA-256, long SVG path outlines (MathJax glyphs) as length + hash.
3. **Shared sections** (`expected/_shared/`): the `.docx` boilerplate and the CSS heads repeat in every case; stored
   once they bring the snapshots from 10.3 MB to 2.7 MB. A change of one shows as a diff of the expanded text.
4. **Fonts in the golden page:** `MathCore.exRatio` sizes a formula by the document font's x-height, measured in
   the page. The suite page has no `@font-face`, so it measured the system's serif fallback (Times New Roman on
   Windows: 0.447; another font on Linux) — formula sizes would differ by machine. `build.js` adds the bundled web
   fonts as faces first (Vazirmatn now measures 0.528, as in the app). Only the two formula cases' snapshots depend
   on it. The builder suite page itself is unchanged. A formula with right-to-left `\text` is still measured
   differently by platform with this same font (§5): its widths are normalised.
5. **The about/guide documents are not in the goldens:** they are the app's content and change with every wording
   edit; they stay in the builder suite and in `docx-validate.js`.
6. **Schemas committed, not downloaded:** 0.68 MB, unchanged files with their SHA-256 and licence, so CI needs no
   network and a moved ECMA URL cannot break it. Transitional, not Strict: docx.js writes Transitional.
7. **Markup Compatibility before validation**, as Word reads the file: docx.js declares `w14 w15 wp14` ignorable;
   validating them against the 2016 schemas would report Office extensions, not errors. With that, the allow-list is
   **empty** — every docx.js part validates as it is.
8. **`docProps/core.xml` is not schema-checked** (its schema imports Dublin Core from dublincore.org); it is
   checked for well-formedness and its content type, and it is in the goldens (dates normalised).
9. **Two `lib/` fixes, both small and proven by a failing check:** `MathCore` (schema), `MarkdownImporter` (unit
   tests). A rule in a table cell becomes a line break — a GFM cell cannot hold a rule; a rule inside running text is
   dropped — Markdown has no inline rule; a rule list item goes into the item before it, so the list is not split.
10. **apt versions pinned to `noble-updates`** (current, with security fixes) rather than the immutable release
    pocket (LibreOffice 24.2.2 of 2024, whose exact-version dependencies would need every LibreOffice package pinned):
    the price is a bump when Ubuntu replaces a version (the step says so).
11. **One workflow of its own** (`builders.yml`), run on every change: `tooling.yml` has no browser or LibreOffice,
    `pdf-lab.yml` runs only on the lab's paths (it keeps its own `roundtrip.js` step). Triggers: every push, every
    pull request and by hand, like `tooling.yml` and `pdf-lab.yml` — so a push to a branch with an open PR runs it
    twice (review finding 12). Kept consistent with the other two (a branch without a PR is checked too); narrowing
    `push` to `main` would be one change for all three workflows.
12. **Markup Compatibility, what is stripped unchecked:** docx.js writes only `w15:restartNumberingAfterBreak` and
    `w15:tentative` from the ignorable namespaces (both ST_OnOff, checked before they are removed); `w14` / `wp14` are
    declared and unused. Any other ignorable element or attribute is removed and listed by the run ("stripped: …",
    today "nothing"), so a new one cannot hide.

## 5. CI

**First CI run** (run 41510527115, job 125500902568, on the P2.4 head with P2.3 unchanged): the pinned install
worked (libxml2-utils `2.9.14+dfsg-1.3ubuntu3.10`, LibreOffice 24.2.7.2), `roundtrip.js` ok (529 pass, 3 known),
the MarkdownImporter tests ok, **xmllint 1,328 / 1,328 parts valid** — and two steps red:

1. **LibreOffice: no PDF for 7 of 76** — `toc-ltr`, `toc-rtl`, `page-breaks`, `hr-in-list-and-cell` and the three
   about documents. Those are exactly the **last seven files** of the single `soffice --convert-to pdf a b c …` call,
   starting at `toc-ltr`; the whole call took 3.4 s and the script read neither soffice's exit status nor its output.
   So the one LibreOffice process stopped at `toc-ltr` (a crash, by everything the log shows) and never reached the
   rest. The same 74 files in one call with LibreOffice 24.2.7.2 for **Windows** convert completely (22 s, 74 PDFs,
   `toc-ltr.pdf` 57 KB), so the failure is Linux-only and cannot be reproduced here.
   **Fix:** one soffice process per file, the profile set up first (`--terminate_after_init`), exit 0 and a new PDF
   required, a failure retried in the same profile and then in a fresh one, and reported with each try's exit status
   / signal and soffice's output; old PDFs deleted first. **Locally, with LibreOffice 24.2.7.2 for Windows and the
   lxml stand-in:** `docx-validate.js` in full — 76 / 76 `.docx` built, 1,328 / 1,328 parts valid, **76 / 76
   converted** (≈ 9 s per file here), one note: the first conversion of the run (`rtl-basic`) ended with exit 0 and
   no PDF and succeeded on the retry — a first-start quirk of a fresh profile on Windows, also seen before the
   set-up step was added; the retry covers it, and it is printed, not hidden. With this, a file LibreOffice cannot
   convert costs only itself and says why; whether `toc-ltr` / `toc-rtl` alone still fail on Ubuntu (the ToC field) is
   what the next CI run shows. If they do, it is a LibreOffice 24.2 crash on a schema-valid file: it goes in the
   report with soffice's message, and the decision then is an allow-list entry with that reason, unless the run
   points at something DocxBuilder writes wrongly (then it is fixed there).
2. **Goldens not deterministic across platforms** — `latex-formulas` and `latex-formulas-mathml`, `export.html` and
   `doc.mhtml.txt`, Case 36 `\text{اگر } x > 0 \text{ آنگاه } y = 1`: `data-width` 8.00 (Windows) vs 7.93 (Ubuntu), the
   SVG's width and viewBox, the `.doc` picture's width. **Cause:** MathJax measures right-to-left `\text` in the page
   (MathCore asks it to, `mtextInheritFont`, so the text is drawn in Vazirmatn): `measureTextNode` puts an SVG
   `<text>` in a 1ex-wide SVG at the page's text size (≈ 14 px here) and reads `getBBox`. The font is the same file
   on both machines — `build.js` registers the bundled Vazirmatn as a face and the SVG names it (`font-family:
   Vazirmatn`; Windows measures 7.997 em with it) — so the difference (0.063 em over the two words) comes from how
   each platform lays out text at that small size; the likely mechanism is glyph advances rounded to whole pixels on
   Linux (no subpixel positioning) and not on Windows. Not proven here (no Linux machine), but either way a property
   of the platform's text rendering, not of the font choice: it cannot be pinned from Kelk's side without changing
   how MathJax measures. **Fix:** for a formula whose TeX holds a right-to-left letter only, the
   measured values (`data-width`, the SVG's width, viewBox width and `translate` x, the `.doc` picture's width and its
   PNG's size) become `[measured]` in the snapshots; the TeX, MathML, glyph outlines and heights stay. Regenerated for
