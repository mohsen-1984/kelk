## 2. Line endings on Windows working trees

With `core.autocrlf=true` this machine's working tree had **267 text files in CRLF** (index LF) — including the corpus
`.md` sources the lab scores against. After the change a checkout gives LF everywhere. To be sure the CRLF-to-LF switch
does not move scores, the corpus was run on both:

- CRLF working tree ("before") and LF working tree ("after"): **all 144 Markdown outputs byte-identical**, scores identical.

So the lab does not depend on line endings today, and `eol=lf` keeps it that way for the other contributor's machine and CI.

## 5. PDF storage — decided: (1) ordinary files

**Measured:** 144 PDFs, all in `tests/pdf-lab/pdf/`, 15.57 MiB raw, **9.94 MiB in the pack** (34 % of the 28.86 MiB
`.git` pack). Every one was added in a single commit (`8229e6d`, PR #1); none has changed since. They are read by
`env.js`, `run-import.js`, `features.js`, `profile.js`, `struct.js` and the CI stress step. About 45 `make-*` scripts
regenerate them, but they need Chrome, LibreOffice, wkhtmltopdf, Prince, iText, ReportLab, Tesseract — CI cannot
rebuild the corpus, and no script pins `CreationDate` / `ID`, so any regeneration yields a whole new binary.

| | (1) Ordinary files + `binary` | (2) Git LFS from now on | (3) Release asset + `scripts/fetch-pdfs.js` |
|---|---|---|---|
| Clone size now | 28.9 MiB | 28.9 MiB — history keeps the blobs (`git lfs migrate` would rewrite history: not allowed) | 28.9 MiB, same reason |
| Growth per regenerated PDF | full blob, ≈ 70 KB packed on average | a pointer; the blob counts against LFS storage | none in git; a new asset version |
| CI | works today (`lfs: false`) | `lfs: true` on both checkouts (head and base), ≈ 31 MB LFS bandwidth per run; the free 10 GiB / month ≈ 320 runs, then LFS is blocked for the month | a fetch step for head and base, plus a cache; the base commit must name its asset version |
| Contributors | nothing to do | `git lfs install` on both machines; without it, pointer files and confusing lab failures | online for the first run; forks depend on the release |
| Pages (until P8.1) | serves the PDFs (dead weight, removed by P8.1's include list) | serves pointer text | nothing |
| Risk | grows only on deliberate regeneration | mixed state (old blobs + LFS); quota tied to the owner account | manifest and asset kept in sync by hand; base-vs-head breaks if an asset is replaced in place |

**Recommendation: (1) keep them as ordinary files marked `binary`** (already in the new `.gitattributes`). The
15.6 MB is paid and stays in history whatever is chosen; the files have never changed and only change by a deliberate,
reviewed rebuild on a machine with the producer tools. LFS helps only future versions and makes CI, both machines and
the owner's quota depend on it; a release asset adds versioning work for fixtures a base-vs-head gate must read at two
commits. This matches the owner's earlier lean.

If (1) is chosen: `pdf-lab.yml` keeps `lfs: false`; the plan's P0.1 text (LFS "recommended", "1 GB/month quota" — the
free quota is now 10 GiB storage / 10 GiB bandwidth) and P0.3's "`lfs: true`" item are corrected in the approval step;
`tests/pdf-lab/README.md` gains a line: commit a regenerated PDF only when its content changed.

**Revisit when** `tests/pdf-lab/pdf` passes 50 MB, PDF changes add > 10 MB of packed blobs in a year, a single fixture
exceeds 10 MB, or the pack passes 100 MiB — then move *new* large or churning fixtures to (3) with a versioned asset
name and a committed SHA-256 manifest (preferred to LFS).

Source for the quota: [GitHub docs — Git LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)
(checked 1405-08-10).
